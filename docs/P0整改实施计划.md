# 家谱系统 P0 整改实施计划

> **For Hermes:** 按本计划推进 P0 六项整改，优先产出结构稳定性，再做页面与规则收口。

**Goal:** 完成家谱系统 P0 六项结构整改任务，固定系统边界、字段分层、权限底线、页面职责、设置结构与最小审计闭环。  
**Architecture:** 先文档与规则收口，再映射到前后端代码与页面结构，最后用最小验证闭环确认系统没有继续发散。  
**Tech Stack:** FastAPI backend、Vue3 + Element Plus frontend、SQLite/本地备份、现有审计与权限体系。

---

## 范围说明

本计划只覆盖以下 P0 六项：

1. 明确三大子系统边界
2. 明确成员字段分层
3. 收紧结构级权限
4. 固定成员录 / 详情抽屉 / 编辑表单职责
5. 拆清系统设置内部结构
6. 明确审计最小闭环

本计划默认先做“结构整改”，不是继续追加零散功能。

## Task 4：梳理并收紧结构级权限

**Objective:** 明确哪些字段是高敏结构字段，并在前后端都收紧。  

**Files:**
- Modify: `docs/家谱系统字段分层与权限矩阵.md`
- Inspect/Modify: `backend/main.py`
- Modify: `frontend/src/components/MemberForm.vue`
- Modify: `frontend/src/components/SettingsPanel.vue`
- Reference: `frontend/src/views/WorkspaceView.vue`

**Step 1: 定义结构级字段清单**

必须纳入高敏控制：
- `fatherId`
- `motherId`
- `spouseIds`
- `generation`
- `branch`
- `isCoreMember`

**Step 2: 检查后端接口是否真有限制**

重点检查：
- 成员创建接口
- 成员更新接口
- 是否区分普通编辑与结构编辑
- 是否仅靠前端隐藏按钮（如果是，要补后端限制）

**Step 3: 前端表单按权限禁用/隐藏结构字段**

编辑者默认：
- 可看结构字段
- 不可随意改结构字段

管理员/超级管理员：
- 可改，但应有更高提示

**Step 4: 验证**

验收标准：
- 编辑者不能通过常规 UI 修改结构骨架
- 即便绕过 UI，请求也会被后端拒绝或过滤
- 高敏字段有明确权限策略，不再跟普通档案字段同级对待

## Task 5：固定成员录 / 详情抽屉 / 编辑表单职责

**Objective:** 让三个核心界面分工稳定，不再互相侵入。  

**Files:**
- Modify: `docs/系统边界与模块职责清单.md`
- Modify: `frontend/src/components/MembersPanel.vue`
- Modify: `frontend/src/components/MemberDrawer.vue`
- Modify: `frontend/src/components/MemberForm.vue`

**Step 1: 成员录职责冻结**

明确成员录只负责：
- 搜索
- 筛选
- 质检
- 快速进入详情/编辑

不负责：
- 深度档案阅读
- 复杂结构编辑流程

**Step 2: 详情抽屉职责冻结**

明确详情抽屉只负责：
- 阅读档案
- 看关系
- 跳转树定位
- 进入编辑

不负责：
- 承载完整大表单

**Step 3: 编辑表单职责冻结**

明确编辑表单只负责：
- 创建成员
- 编辑字段
- 权限内修正结构/档案信息

不负责：
- 长时间阅读
- 多成员治理

**Step 4: 验证**

验收标准：
- 三个页面/组件职责边界能用一句话清晰说明
- 后续新增需求能快速判断应落在哪个组件
- 页面没有继续朝“万能组件”方向膨胀

## Task 7：建立最小审计闭环

**Objective:** 先把关键结构与治理操作纳入审计，形成可追溯底线。  

**Files:**
- Modify: `docs/家谱系统字段分层与权限矩阵.md`
- Inspect/Modify: `backend/main.py`
- Inspect/Modify: 审计相关存储/接口（以现有实现为准）
- Modify: `frontend/src/components/SettingsPanel.vue`（如涉及审计显示）

**Step 1: 确认当前已有的审计能力边界**

检查：
- 当前记录了哪些操作
- 是否记录字段变更前后值
- 审计页是否能区分登录、成员更新、设置修改等

**Step 2: 定义“P0 必审计”清单**

必须覆盖：
- 父母关系修改
- 配偶关系修改
- 主线标记修改
- 世代 / 支系修改
- 来源修改
- 删除成员
- 用户启停
- 密码重置
- 设置修改

**Step 3: 若现有审计不足，补最小字段记录能力**

至少记录：
- 操作人
- 操作时间
- 操作对象
- 操作类型
- 关键字段变化摘要

**Step 4: 验证**

验收标准：
- 关键结构和治理动作可回查
- 审计页能看出谁在什么时候改了什么
- P0 结束后系统具备最小可追溯能力

## Task 8：形成 P0 验收清单并逐项复核

**Objective:** 用一份统一验收清单关闭本轮整改。  

**Files:**
- Create: `docs/P0验收清单.md`
- Reference: 本计划涉及的所有文档与组件

**Step 1: 写验收清单**

至少按六项整改列出：
- 是否完成
- 证据文件
- 影响页面/接口
- 是否仍有遗留风险

**Step 2: 用人工 walkthrough 方式逐项核对**

重点核对：
- 文档是否一致
- 页面职责是否清楚
- 表单/详情/成员录是否按分层组织
- 权限是否只停留在前端表象
- 审计是否真正覆盖关键动作

**Step 3: 输出遗留问题列表**

把未做但被发现的重要问题单列，转入 P1，而不是偷偷混进 P0。

**Step 4: 验证**

验收标准：
- P0 六项均可被明确判定完成/未完成
- 遗留项已转入下一阶段，不留灰区
