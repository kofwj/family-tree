# P0 现状差距清单 v2（带文件级改动建议）

## 1. 文档目的

本文档基于当前代码现状，对照 P0 六项结构整改目标，输出一版更贴近落地执行的差距清单。

本版本重点覆盖以下文件与模块：

- `frontend/src/components/SettingsPanel.vue`
- `frontend/src/components/TreePanel.vue`
- `backend/main.py` 中与权限、审计、成员写入相关的实现

对照维度统一为：

- 当前已有
- 当前缺失
- 风险点
- 建议改动位置

---

## 2. 总体结论

当前系统并不是“没结构”，而是已经有了明显的结构雏形，但还没有彻底固化为稳定规则。

### 当前已经成型的部分
- 前端已有 Tree / Members / Settings / Backup 四大页面模块
- 成员表单已有字段分区
- 成员详情抽屉已偏阅读化
- 成员录已明显偏资料治理工作台
- 后端已有角色能力模型 `ROLE_CAPABILITIES`
- 后端已有字段可见范围模板
- 后端已有审计表 `AuditLog`
- 后端已有统一能力检查 `require_capability(...)`
- 后端已有成员字段过滤函数 `filter_member_payload_for_user(...)`

### 当前最核心的差距
- 页面边界仍然主要靠“约定”，还不是“硬约束”
- 设置页治理职责过于集中，尚未分区
- TreePanel 仍缺少“只读关系浏览器”的明确产品约束
- 后端权限虽有能力模型，但字段级策略仍不够严谨
- 审计虽然已存在，但“关键字段专项审计”仍不够明确
- 字段分层没有形成单一事实来源，仍散落在多个组件和函数里

# 3. P0-1 明确三大子系统边界
目标：
- 树 = 看关系
- 成员录 = 治资料
- 设置 = 管系统

## 当前已有
### 前端结构层面已具备一级边界
在 `WorkspaceView.vue` 中，已经按 tab 区分为：
- 家族世系
- 成员录
- 族谱备份
- 系统设置

对应的组件边界也存在：
- `TreePanel.vue`
- `MembersPanel.vue`
- `ArchivePanel.vue`
- `SettingsPanel.vue`

这说明一级信息架构已经不是空白，而是已有明确雏形。

## 当前缺失
### 缺失 1：TreePanel 的“只读浏览器”定位还没有被正式写死
`TreePanel.vue` 当前职责非常纯：
- 展示节点和边
- 点击节点触发 `node-click`
- 聚焦到当前成员

这是好事，但它目前更像“刚好还比较轻”，而不是“已经被明确限制只能做浏览器”。

也就是说：
- 现在它没有多余功能
- 但后续很容易被继续加编辑、筛选、治理功能

### 缺失 2：SettingsPanel 已经成为多治理职能混合容器
在 `SettingsPanel.vue` 中，目前已混合承载：
- 基础设置
- 字段模板
- 用户管理
- 权限说明
- 最近操作审计

这说明“设置 = 管系统”方向是对的，但模块内部已经过载，缺少更清晰的信息分区。

### 缺失 3：Tree / Members / Settings 的产品级边界未体现在代码注释或设计约束中
当前代码更多体现为功能存在，而不是边界规则存在。

## 风险点
- 后续谁接手谁都可能继续往 TreePanel 里塞操作能力
- SettingsPanel 会继续膨胀成大杂烩治理页
- 新需求落地时缺少“先归类后实现”的约束

## 建议改动位置
### 建议优先修改文件
- `frontend/src/views/WorkspaceView.vue`
- `frontend/src/components/TreePanel.vue`
- `frontend/src/components/SettingsPanel.vue`

### 具体建议
1. 在 `TreePanel.vue` 文件头部或组件注释中明确：
   - 本组件只负责关系浏览、定位、节点点击跳转
   - 不承载成员编辑、质检治理、权限操作

2. 在 `SettingsPanel.vue` 内部先做逻辑分区，即使暂时不拆文件，也至少按以下区块划清：
   - 基础设置
   - 字段模板 / 展示策略
   - 用户与权限
   - 审计中心

3. 在工作区层面明确“新增需求归属规则”：
   - Tree：关系浏览
   - Members：资料治理
   - Settings：治理与系统控制

### 前端表单与详情也已有分区雏形

说明前后端都已有“分层意识”。

## 当前缺失
### 缺失 1：分层并未形成统一配置源
目前字段分层逻辑仍然散落在多个地方：
- `backend/main.py` 的 `CORE_RELATION_FIELDS`
- `backend/main.py` 的 `PROFILE_FIELDS`
- `MemberForm.vue` 的表单分区
- `MemberDrawer.vue` 的阅读分区
- `MembersPanel.vue` 的完整度字段和显示列

这会导致后续维护时出现：
- 一处改了，另一处忘了
- 页面分组和权限分组不同步

### 缺失 2：系统控制层在前端没有独立呈现为治理层
虽然 `isPublic` 已存在，但目前在 `MemberForm.vue` 中它和“宗谱信息”并列放在同一区域里，容易造成误解。

### 缺失 3：结构字段和档案字段的视觉区分还不够强
特别是在编辑表单里：
- `generation / branch / isCoreMember / fatherId / motherId / spouseIds`
- 与普通档案字段虽然分区了，但高敏感属性提示不足

## 风险点
- 后续字段扩展时语义持续漂移
- 权限、审计、表单、详情可能各自维护一套字段分类
- 结构字段与普通档案字段混同，影响后续权限和审核流落地

## 建议改动位置
### 建议优先修改文件
- `backend/main.py`
- `frontend/src/components/MemberForm.vue`
- `frontend/src/components/MemberDrawer.vue`
- `frontend/src/components/MembersPanel.vue`

### 具体建议
1. 在后端补一个统一字段分层常量，例如：
   - `IDENTITY_FIELDS`
   - `STRUCTURE_FIELDS`
   - `ARCHIVE_FIELDS`
   - `SYSTEM_FIELDS`

2. 让 `CORE_RELATION_FIELDS` 和 `PROFILE_FIELDS` 不再只是一种权限切分，而是从字段分层常量派生。

3. 在 `MemberForm.vue` 中把 `isPublic` 挪到单独“系统控制 / 展示控制”区块。

4. 在 `MemberDrawer.vue` 中把“资料维护”明确为治理附加区，而不是档案主体区。

# 5. P0-3 收紧结构级权限
目标：
- 结构字段和普通档案字段分权
- 编辑者默认不能改骨架

## 当前已有
### 后端已有能力模型
`backend/main.py` 已有：
- `ROLE_CAPABILITIES`
- `require_capability(...)`
- `get_user_capabilities(...)`

其中：
- `super_admin` / `admin` 拥有 `member.edit_core_relation`
- `editor` 没有 `member.edit_core_relation`

### 后端已有字段过滤入口
`filter_member_payload_for_user(...)` 已存在：

- 有 `member.edit_core_relation`：允许 `PROFILE_FIELDS | CORE_RELATION_FIELDS`
- 只有 `member.edit_profile`：允许 `PROFILE_FIELDS`，外加在 `member.create` 时允许 `father_id / mother_id / spouse_ids`

### 前端表单已有部分高敏字段禁用
`MemberForm.vue` 中这些字段已受 `canEditCoreRelation` 控制：
- `isCoreMember`
- `spouseIds`
- `fatherId`
- `motherId`

说明当前已经有“前后端双层收紧”的雏形。

## 当前缺失
### 缺失 1：结构字段收紧范围还不完整
根据 `backend/main.py`：

`CORE_RELATION_FIELDS` 目前包含：
- `generation`
- `generation_name`
- `rank_no`
- `rank_title`
- `branch`
- `is_core_member`
- `spouse_name`
- `spouse_ids`
- `father_name`
- `father_id`
- `mother_name`
- `mother_id`

说明后端把这些都视为结构级字段。

但在前端 `MemberForm.vue` 里，目前仅以下字段被禁用：
- `isCoreMember`
- `spouseIds`
- `fatherId`
- `motherId`

前端尚未同步收紧：
- `generation`
- `generationName`
- `rankNo`
- `rankTitle`
- `branch`

这会造成：
- 前端把一部分结构字段当普通字段展示为可编辑
- 后端再静默忽略或拒绝
- 用户体验与真实权限不一致

### 缺失 2：编辑者创建成员时允许带父母/配偶结构字段，这是一个折中规则，但未被清晰表达
当前后端允许：
- 编辑者在新增成员时提交 `father_id / mother_id / spouse_ids`

这个规则本身未必错，因为新增成员必须挂到分支里。
但它需要在产品文档与表单交互上被明确，否则会形成“编辑者不能改关系，但能在创建时带关系”的认知落差。

### 缺失 3：前端没有高敏字段可视化提示
目前只是禁用，缺少：
- 为什么不能改
- 哪些字段属于结构骨架
- 需要什么权限才能改

## 风险点
- 前后端权限表达不一致
- 高敏字段被误认为普通资料字段
- 创建流程和编辑流程的结构权限不一致，会让后续维护规则变复杂

## 建议改动位置
### 建议优先修改文件
- `backend/main.py`
- `frontend/src/components/MemberForm.vue`

### 具体建议
1. 在前端同步把以下字段视为结构级：
   - 世代
   - 字辈
   - 排行序号
   - 排行称谓
   - 支系
   - 主线标记
   - 父母
   - 配偶

2. 在 `MemberForm.vue` 为这些字段增加统一样式或说明，例如：
   - “结构字段”标签
   - “需高级权限修改”提示

3. 在后端继续保留 `filter_member_payload_for_user(...)` 作为兜底，不依赖前端限制。

4. 后续如要进一步收紧，可考虑把“编辑者创建成员可附带父母关系”单独写成显式规则。

# 6. P0-4 固定成员录 / 详情抽屉 / 编辑表单职责
目标：
- 成员录 = 治理
- 抽屉 = 阅读
- 表单 = 录入

## 当前已有
### 成员录已明显承担治理职能
`MembersPanel.vue` 当前已经包含：
- 搜索
- 性别 / 世代筛选
- 数据质量视图
- 低完整度阈值
- 缺来源 / 缺传略 / 缺关系筛选
- 表格 / 卡片视图

这说明成员录已经基本是“资料治理工作台”。

### 详情抽屉已明显偏阅读
`MemberDrawer.vue` 当前主要是：
- 档案完整度
- 身份与宗谱信息
- 生命轨迹
- 关系阅读
- 人物档案阅读
- 资料来源查看

操作按钮只在底部：
- 在家谱中定位
- 编辑补全
- 删除

这是典型的阅读型结构。

### 表单已明显偏结构化录入
`MemberForm.vue` 当前：
- 以分区表单为主
- 直接承担录入与修正职责
- 没有塞过多阅读型内容

## 当前缺失
### 缺失 1：详情抽屉中“资料维护”区仍带有治理语义
`MemberDrawer.vue` 中的“六、资料维护”实际上是治理信息，不完全属于人物档案阅读本体。

这不是严重问题，但如果继续往里加：
- 审计
- 审核
- 来源治理
- 完整度处理

就会使抽屉再次从“阅读页”膨胀为“混合操作页”。

### 缺失 2：表单中缺少“结构字段高敏感提示”
虽然职责已经是录入，但它还没有对高敏字段进行更强的认知区分。

### 缺失 3：成员录和抽屉之间的治理边界尚未通过说明固定
现在是“实际比较合理”，但还没有被写成规则。

## 风险点
- 后续功能迭代时，治理动作重新流入抽屉
- 表单继续膨胀，变成阅读+录入一体页
- 成员录和详情抽屉再次职责串味

## 建议改动位置
### 建议优先修改文件
- `frontend/src/components/MemberDrawer.vue`
- `frontend/src/components/MemberForm.vue`
- `frontend/src/components/MembersPanel.vue`

### 具体建议
1. 在 `MemberDrawer.vue` 中将“资料维护”定义为治理附加区，并控制其扩张。
2. 在 `MemberForm.vue` 中加入高敏字段说明，强化“表单负责改、抽屉负责看”的心智。
3. 在成员录区域标题或说明中明确其是“资料治理工作台”。

   - `SettingsBasicSection.vue`

   - `SettingsUserSection.vue`

# 8. P0-6 明确审计最小闭环
目标：
- 关键结构变更可回溯
- 关键治理操作可回溯

## 当前已有
### 后端审计基础设施已存在
在 `backend/main.py` 中已有：
- `AuditLog` 模型
- `write_audit_log(...)`
- `audit_log_payload(...)`
- `/admin/audit-logs`

说明审计不是待设计项，而是已经落地。

### 已确认已有审计的操作
从后端接口代码看，以下操作已写审计：
- `auth.login`
- `user.create`
- `user.update`
- `user.disable`
- `user.enable`
- `user.reset_password`
- `settings.update`
- `member.create`
- `member.update`
- `member.delete`
- `member.import_excel`
- `member.import_default`

说明“最小审计闭环”已经有了较强基础。

## 当前缺失
### 缺失 1：成员更新审计虽然有，但没有对关键结构字段做专项识别
`update_member(...)` 当前做法是：
- 生成 `before`
- 生成 `after`
- 对 `data.keys()` 做通用 diff
- 统一写入 `member.update`

这意味着：
- 审计有记录
- 但没有突出“这是父母关系变更”“这是主线标记变更”“这是支系变更”

对于后续审核和追责来说，仍然偏粗。

### 缺失 2：SettingsPanel 审计视图仍是“列表查看”，不是结构化治理视图
前端只是展示：
- 时间
- 操作人
- 动作
- 对象
- 简略详情

还没有：
- 关键结构变更高亮
- 类型过滤
- 成员维度过滤
- 用户维度过滤

### 缺失 3：备份相关能力虽有 capability 定义，但当前本轮未核到完整前端治理入口与更细粒度审计使用方式
后端 capability 里包含：
- `backup.view`
- `backup.create`
- `backup.download`
- `backup.delete`
- `backup.restore`

但本次聚焦文件中，设置页尚未形成完整备份治理中心表达。

## 风险点
- 虽然有审计，但关键结构修改不够醒目
- 后续做审核流时，无法快速聚焦高风险变更
- 审计数据存在，但治理价值释放不足

## 建议改动位置
### 建议优先修改文件
- `backend/main.py`
- `frontend/src/components/SettingsPanel.vue`

### 具体建议
1. 在 `update_member(...)` 中，对高敏字段单独识别，例如：
   - `fatherId`
   - `motherId`
   - `spouseIds`
   - `generation`
   - `branch`
   - `isCoreMember`
   - `source`

2. 审计 detail 中可以加入字段类别，例如：

# 11. 结论

从当前代码看，P0 最大的价值不是“重写系统”，而是：

- 把已经存在的结构雏形正式固化

**当前系统最需要的不是大拆大建，而是把已有结构从“隐含规则”升级为“明确规则 + 文件级落地约束”。**
